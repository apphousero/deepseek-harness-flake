# dsh

Nix flake packaging [`deepseek-ai/deepseek-harness`](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) as a
package, an overlay, and a Home Manager module. Upstream ships no release binaries: the only distribution channel
is the npm package [`@deepseek-ai/dsh`](https://www.npmjs.com/package/@deepseek-ai/dsh), which is what this flake
builds. For how `dsh` itself works, read the shipped JS in the store closure or
[the developer docs](https://deepseek-harness.github.io/deepseek-harness/en/guide/quickstart) — the marketing page
at deepseek.com/harness has no packaging-relevant detail.

| File | Purpose |
| --- | --- |
| `package.nix` | The derivation. Version and the pnpm store hash live here. |
| `npm/` | The install root: `package.json` pinning one exact `@deepseek-ai/dsh` version, `pnpm-lock.yaml`, and `pnpm-workspace.yaml` (`nodeLinker: hoisted`). |
| `flake.nix` | Outputs: `packages`, `checks`, `formatter`, `apps.update`, `devShells`, `overlays.default`, `homeManagerModules.default`. |
| `module.nix` | Home Manager module: `programs.deepseek-harness.{enable,package,patches}`. |
| `tests/module.nix` | Evaluates `module.nix` against a stub Home Manager and asserts the rendered `cordis.patch.yml`. |
| `update.sh` | Rewrites version, lock, and hash. Exposed as `nix run .#update`. |

There is no NixOS module by design: `dsh` keeps every byte of user state under `$DSH_HOME` (`~/.dsh`), so a system
module would only wrap `environment.systemPackages`. The overlay is the NixOS path.

## Packaging model: npm release, pnpm lock, no source build

`package.nix` installs the published npm package into a store closure and wraps its `bin.js` with `node`. It does
**not** check out the upstream monorepo, and it does not use `buildNpmPackage`.

Each of these was reproduced before the decision:

1. **No release assets.** `deepseek-ai/deepseek-harness` publishes tags (`dsh-v0.1.0-rc.8`) with zero binary
   assets. There is no `SHA256SUMS.txt` and nothing to hash-pin except npm tarballs.
2. **npm cannot resolve this graph.** `npm install --package-lock-only` on `@deepseek-ai/dsh` ran 20 minutes at
   100% CPU and 3.4 GB RSS without producing a lockfile — the ~500-package graph with dense peer dependencies is
   pathological for Arborist. pnpm resolves the same graph in 4 seconds. That rules out `buildNpmPackage` and
   `importNpmLock`, both of which need a `package-lock.json`.
3. **A source build buys nothing.** `pnpm install && pnpm run build` over the monorepo produces the same JS the
   registry already publishes, in exchange for building several hundred workspace packages.

Consequences worth preserving:

- The lock is generated by the **pinned nixpkgs pnpm** (`pnpm_11`, currently 11.21.0). `fetchPnpmDeps` refuses a
  `lockfileVersion` newer than the pnpm major it runs, and `pnpmConfigHook` fails on a config mismatch. Do not
  regenerate `npm/pnpm-lock.yaml` with a random host pnpm; `nix run .#update` and `nix develop` both give you the
  pinned one.
- `fetcherVersion = 4` is the current `fetchPnpmDeps` contract (SQLite dump for reproducibility). Lowering it
  changes the hash; 1 and 2 are deprecated and slated for removal.
- `fetchPnpmDeps` fetches with `--force`, so the store holds every platform's optional packages and **one hash
  covers all three systems**. Do not add per-system hashes.

## Native code in a "JavaScript" package

The closure contains prebuilt native artifacts, so this is not a `stdenvNoCC` package and `autoPatchelfHook` is
load-bearing on Linux: `node-pty` (`pty.node`), `sharp` plus `@img/sharp-libvips-*` (`libvips-cpp.so`),
`@koromix/koffi-*`, and `node-addon-require-builtin-*`. They need `stdenv.cc.cc.lib` for `libstdc++`/`libgcc_s`.
`@vscode/ripgrep` and `@deepseek-ai/node-addon-landlock-run` ship static binaries and need nothing.

`installPhase` deletes `@koromix/koffi-*/musl_*`: koffi ships both a glibc and a musl payload, and the musl one
wants `libc.musl-<arch>.so.1`, which no glibc stdenv can satisfy. Without the deletion `autoPatchelfHook` fails
the build. Do not "fix" this with `autoPatchelfIgnoreMissingDeps` — that keeps an unloadable `.node` in the
closure and hides the next real missing library.

The `installCheck` loads `node-pty`, `sharp`, and `node-addon-require-builtin` through a `createRequire` anchored
at the installed `@deepseek-ai/dsh/package.json`. That is the only check that proves patchelf did its job; a
missing library otherwise surfaces at runtime, in a plugin, on a user's machine.

## Runtime model

`dsh` needs a writable `$DSH_HOME` (`~/.dsh`, overridable by the env var):

- `~/.dsh/profiles/<name>/` is auto-initialized on first use (`package.json` with `dsh.profile.bundles`,
  `cordis.patch.yml`, `pnpm-workspace.yaml`).
- `~/.dsh/profiles/node_modules/` gets one symlink per package in the installation's dependency closure, pointing
  into the store. It is re-pointed idempotently, so a version bump heals it — but a *real directory* at that path
  makes `dsh` throw, by design.
- `~/.dsh/cordis.patch.yml` is the home-level user patch layer, which is what the Home Manager module writes.

The wrapper only appends `pnpm` to `PATH`: `dsh plugin` is a pnpm forwarder that installs out-of-tree plugins into
the profile directory. `git` is deliberately not in the closure — git-hosted plugin specs use the user's git.

## Updating to a new version

```sh
nix run .#update              # the latest npm dist-tag
nix run .#update -- 0.1.0-rc.7 # a specific version
```

The script rewrites `npm/package.json`, regenerates `npm/pnpm-lock.yaml`, rewrites `version` in `package.nix`, and
then resolves the pnpm store hash by blanking it, building `.#deepseek-harness.pnpmDeps`, and reading the `got:`
line out of the mismatch. It is idempotent: when neither the version nor the lock moved it restores the previous
hash and fetches nothing.

Two accounting rules keep a silent no-op from looking like a bump: the awk pass fails unless it rewrote exactly
one `version` line and exactly one `hash` line, and the script fails if the regenerated lock has no
`'@deepseek-ai/dsh@<version>':` entry (an unpublished or mistyped version).

Upstream publishes prereleases only, and `dist-tags.latest` currently trails `next` (rc.7 vs rc.8). The script
follows `latest` on purpose; pass a version explicitly to track `next`.

### CI

`.github/workflows/check.yml` is the only definition of "checked": a per-system matrix running `nix flake check -L`
and `nix run .#deepseek-harness -- --version`. It is both an ordinary `push`/`pull_request` workflow and a
`workflow_call` reusable one, taking an optional `version` input that applies a pending bump before checking, and
an optional `digest` pinning what that bump must produce.

Each leg first asserts `builtins.currentSystem` equals its `matrix.system`. Without that the matrix is decorative:
`nix flake check` only ever checks the host, so a runner label that silently changes architecture buys a row of
green runs covering one system.

`.github/workflows/update.yml` runs daily at 06:00 UTC in three jobs: `resolve` runs `update.sh` and reports
whether the pin moved, `verify` calls `check.yml` with the new version, and `pull-request` opens or updates
`update/deepseek-harness`.

The ordering is not decoration. **Pull requests opened with `GITHUB_TOKEN` cannot trigger workflows**, so the PR
shows no checks of its own; the verification has to happen in the update run, before the PR exists. Two
consequences: the repo setting *Allow GitHub Actions to create and approve pull requests* must stay enabled, and
scheduled runs only fire from the default branch.

The digest is `sha256sum package.nix npm/package.json npm/pnpm-lock.yaml | sha256sum` — three files, because a
bump moves all three. Re-deriving beats passing an artifact around, but only the digest makes that assumption
enforced: caret ranges in the transitive graph resolve against live registry state, so a dependency published
mid-run changes the lock, diverges from the digest, and fails the run instead of quietly landing a PR nothing
verified.

### Verifying a bump

```sh
nix flake check -L                                    # package build + module test + formatting
nix build .#deepseek-harness --no-link --rebuild      # reproducibility
nix run .#deepseek-harness -- --version               # expect <version>, bare
nix run .#deepseek-harness -- web --no-open           # boots the whole plugin tree; expect a served UI
```

`nix flake check` is meaningful here only because `checks.<system>.package` aliases the real derivation. A wrong
store hash fails at fetch time; a stale `version` fails the `installCheck` assertion; an unpatched native addon
fails the addon-load probe.

`nix flake check` covers the host system only. `--all-systems` tries to *build* the others and will fail
off-platform; to check that the other systems still evaluate, use
`nix eval .#packages.<system>.deepseek-harness.drvPath`.

## Gotchas

- **`installCheck` needs a writable `HOME`.** `dsh --dump-default-config` initializes `~/.dsh/profiles/web` and
  the module fallback directory before it can compose a tree. Keep `export HOME=$(mktemp -d)`.
- **`dsh --version` prints a bare version** (`0.1.0-rc.8`), not `dsh/<version>`. The assertion compares exactly.
- **Untracked files are invisible to `nix flake check` and to `update.sh`.** The flake source is the git tree, so
  a new file must be `git add`-ed before `checks` or a `pnpmDeps` fetch can see it.
- **`programs.deepseek-harness.patches` is a YAML *list*, not a mapping.** The option type is
  `listOf yaml.type` for that reason. It also cannot express the `!!js` tags a hand-written patch layer may use;
  those belong in a profile's own layer.
- **The closure is ~250 MB.** That is the published dependency graph (AWS, Google, Anthropic, OpenAI SDKs, sharp,
  ripgrep); it is not a packaging mistake. Do not prune `node_modules` by hand — plugins resolve dynamically, and
  a missing package surfaces only when a user mounts that plugin.
- **`x86_64-darwin` was left out on purpose; do not add it.** nixpkgs is retiring the platform: it evaluates on
  `nixos-26.05` with a deprecation warning and is a hard error from 26.11 on. Rosetta covers the remaining users.

## Style

Per the user's global instruction: no comments in Nix source. If one is genuinely unavoidable, keep it to a single
line. Explanatory context belongs in this file or in the commit message. Run `nix fmt` before committing;
`checks.formatting` enforces it.
